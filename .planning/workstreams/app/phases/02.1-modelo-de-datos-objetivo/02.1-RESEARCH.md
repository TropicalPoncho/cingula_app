## Summary

The phase is a big-bang identity change (int id -> uuid) plus a schema split, done in two independent migrations (SQLite on the phone, Postgres on Neon) that MUST agree on the ids of anything they create independently. The single most important design finding: **the auto-created obras (one per path) and the portal-paths (one per standalone trigger) must get deterministic uuid v5 ids** derived from the source uuid, in Dart AND in the Node migration script. Otherwise the server migration and the phone migration each invent different obras for the same path, and the first sync after the cutover duplicates every obra. With v5, both sides produce byte-identical rows and the phone's full resend is a no-op.

The second most important finding: sqflite runs `onUpgrade` (and the version bump) inside one exclusive transaction, so a thrown exception already rolls the whole migration back atomically (SQLite DDL is transactional). But the existing `AppDatabase.init()` catch block treats ANY open failure as "corrupt DB" and renames `cingula.db` aside and starts a fresh seeded DB. A failing migration would therefore silently swap the user's healthy DB for an empty one (data safe in the renamed file, app looks wiped). That catch must be guarded with a dedicated migration exception. The "automatic rollback to backup" of D-19 is thus mostly atomic-transaction rollback; the backup file is the second safety net (logic bug that passes verification, disk problems) and must be taken BEFORE `openDatabase(version: 7)` runs.

Everything else is deliberately boring: table rebuild with new table names (no RENAME gymnastics), `INSERT..SELECT` with LEFT JOINs, verification with `EXCEPT` diffs in both directions (zero-code "checksum"), sqflite_common_ffi for `flutter test` (verified working on this machine), typed Postgres tables with a single global sequence for `change_seq`, one generic `entity_prev` table + trigger for SYNC-06, a spec-driven JS upsert, and a plain Node script for the Neon migration rehearsed on a throwaway Neon branch.

**Primary recommendation:** Build and test the phone migration as a pure function `migrateToV7(Database db)` (throws on any verification mismatch) against synthetic + copied DBs via sqflite_common_ffi FIRST; wire it into `onUpgrade` plus a pre-open file backup LAST; do the Region deletion before the int->uuid flip to shrink the blast radius.

### Local target schema (SQLite v7) — new table names, distinct from old ones
```sql
CREATE TABLE audios (uuid TEXT PRIMARY KEY, kind TEXT NOT NULL DEFAULT 'grabacion'
  CHECK (kind IN ('grabacion','final')), title TEXT NOT NULL, description TEXT NOT NULL DEFAULT '',
  duration_seconds INTEGER NOT NULL DEFAULT 0, storage_key TEXT, checksum TEXT,
  updated_at INTEGER NOT NULL, deleted_at INTEGER, logical_version INTEGER NOT NULL);
CREATE TABLE audio_local (audio_uuid TEXT PRIMARY KEY, local_path TEXT NOT NULL, remote_url TEXT, download_state TEXT);   -- LOCAL ONLY
CREATE TABLE obras (uuid TEXT PRIMARY KEY, name TEXT NOT NULL, owner_id TEXT, visibility TEXT NOT NULL DEFAULT 'draft'
  CHECK (visibility IN ('draft','private','public')), share_token TEXT,
  cover_lat REAL, cover_lon REAL, cover_min_lat REAL, cover_max_lat REAL, cover_min_lon REAL, cover_max_lon REAL,
  updated_at INTEGER NOT NULL, deleted_at INTEGER, logical_version INTEGER NOT NULL);
CREATE TABLE artistas (uuid TEXT PRIMARY KEY, name TEXT NOT NULL, bio TEXT, user_id TEXT, updated_at INTEGER NOT NULL, deleted_at INTEGER, logical_version INTEGER NOT NULL);
CREATE TABLE obra_artistas (uuid TEXT PRIMARY KEY, obra_uuid TEXT NOT NULL, artista_uuid TEXT NOT NULL, updated_at ..., deleted_at ..., logical_version ..., UNIQUE(obra_uuid, artista_uuid));
CREATE TABLE paths (uuid TEXT PRIMARY KEY, obra_uuid TEXT NOT NULL, kind TEXT NOT NULL DEFAULT 'route' CHECK (kind IN ('route','portal')),
  name TEXT NOT NULL, audio_uuid TEXT, grabacion_uuid TEXT, tolerance_meters REAL NOT NULL DEFAULT 10.0,
  updated_at ..., deleted_at ..., logical_version ...);   -- audio_uuid NULLABLE: tolerates dangling legacy refs
CREATE TABLE triggers (uuid TEXT PRIMARY KEY, path_uuid TEXT NOT NULL, position INTEGER NOT NULL DEFAULT 0,
  name TEXT NOT NULL, description TEXT NOT NULL DEFAULT '', latitude REAL NOT NULL, longitude REAL NOT NULL,
  radius_meters REAL NOT NULL, offset_ms INTEGER NOT NULL DEFAULT 0, updated_at ..., deleted_at ..., logical_version ...);
CREATE TABLE path_progress (path_uuid TEXT PRIMARY KEY, saved_offset_ms INTEGER NOT NULL DEFAULT 0, updated_at INTEGER);   -- LOCAL ONLY
```
- Declare `REFERENCES` for documentation and `PRAGMA foreign_key_check`, but do NOT turn on `PRAGMA foreign_keys` (the app never did; enabling it changes today's delete behaviour, e.g. `deleteById` deletes triggers manually). `onConfigure` is the only place the pragma could be set (it runs outside the transaction) — leave it alone.
- `position` for triggers: initialise as `ROW_NUMBER` order by `(offset_ms, legacy id)` per path — computed in Dart (avoid window functions: Android API 21-28 ships SQLite 3.8-3.22; window functions need 3.25). Confirm in the pre-flight how `GeoTriggerRepository`/monitor order triggers today.
- Avoid SQLite features newer than 3.22: no window functions, `RETURNING`, `DROP COLUMN`, `VACUUM INTO`, generated columns. Upsert (3.24) is also unsafe on API 21-27; use plain INSERT/UPDATE.
- Legacy tables are renamed `legacy_audio_assets`, `legacy_geo_paths`, `legacy_geo_triggers`, `legacy_regions`, `legacy_sync_outbox` at the END of the same transaction (after verification). Since 3.26 RENAME also rewrites REFERENCES in sibling legacy tables — harmless because all legacy tables are renamed together.
- `sync_state.server_cursor` MUST be reset to NULL in the migration: today it holds an ISO timestamp; the new cursor is a `change_seq` number (semantics changed).

### Pattern 1: Migration as a pure, throwing function
```dart
// lib/data/migration/v7_migration.dart  (sketch)
Future<void> migrateToV7(DatabaseExecutor db) async {
  // 0. preflight counts captured BEFORE anything is written
  // 1. CREATE new tables
  // 2. audios/triggers/paths via INSERT..SELECT (LEFT JOIN parent uuid); obras + portal paths via Dart loop (uuid v5)
  // 3. local-only tables: audio_local from audio_assets.local_path/remote_url; path_progress from saved_offset_ms
  // 4. outbox rebuild (see Q7)
  // 5. verify(): throws MigrationVerificationException(report) -> sqflite rolls back the txn
  // 6. rename legacy tables
}
// in AppDatabase._onUpgrade:  if (oldVersion < 7) await migrateToV7(db);   // db here == open txn; do NOT call db.transaction()
```
Verification (all inside the transaction, throw on first failure):
1. Counts: `audios == legacy audio_assets`; `triggers == legacy geo_triggers`; `paths == legacy geo_paths + standalone triggers`; `obras == paths`; `path_progress`/`audio_local` per legacy rows; legacy region count unchanged (20).
2. "Checksum" by two-way `EXCEPT` (empty result both ways):
   `SELECT uuid,name,latitude,longitude,radius_meters,offset_ms FROM geo_triggers EXCEPT SELECT uuid,name,latitude,longitude,radius_meters,offset_ms FROM triggers` and the reverse; same for audios (uuid,title,description,duration_seconds,logical_version,updated_at), audio_local vs legacy (local_path, remote_url), paths (uuid,name,tolerance_meters). No hashing code needed; exact equality is stronger than a hash.
3. Integrity: `PRAGMA foreign_key_check` returns no rows (works without `foreign_keys=ON`); no `triggers.path_uuid` missing in `paths`, no `paths.obra_uuid` missing in `obras`.
4. No `NULL` or duplicate uuid in any new table (PK enforces duplicates by throwing).
5. Files untouched: migration never reads/writes .wav; `audio_local.local_path` copied byte-for-byte.

### Pattern 2: Backup BEFORE the upgrading open, then guard init()
`onUpgrade` cannot safely copy its own open DB. In `AppDatabase.init()`, before `openDatabase(version: 7)`:
1. If the file exists: `openDatabase(path)` without `version`/callbacks (no upgrade), read `PRAGMA user_version`, run `PRAGMA wal_checkpoint(TRUNCATE)` (harmless when not WAL), close.
2. If `user_version < 7`: copy `cingula.db` (+ `-wal`/`-journal`/`-shm` sidecars if present) to `cingula.db.pre-v7-<formatRecoveryTimestamp>` (reuse `formatRecoveryTimestamp`). Verify by opening the copy read-only and comparing row counts of the 4 legacy tables. If the backup fails, abort startup — do not migrate.
3. `openDatabase(version: 7, onUpgrade: ...)`.
4. Wrap in `try { } on MigrationException { rethrow-to-UI }` **before** the generic `catch` that calls `renameCorruptDatabase`. Catch ordering matters: without it, a migration failure renames the healthy v6 DB and creates an empty seeded v7 DB. After the rollback the file is still a valid v6 DB: the app cannot run new code on it, so `main.dart` must show a minimal blocking error screen ("la migración falló, tus datos están intactos, respaldo en <ruta>") — reuse the existing `DatabaseRecoveryEvent` banner pattern for the success notice ("migrado; respaldo en …").
5. Backup retention: keep forever. Do NOT build a "delete backup" action (project memory: no destructive actions reachable from UI). "Until the user confirms" = the notice is dismissed; the user can remove the file manually.

### Anti-Patterns to Avoid
- Calling `db.transaction()` inside `onUpgrade` (already inside the exclusive transaction -> deadlock/nesting).
- Renaming the old table to the new name in place (`ALTER TABLE RENAME` rewrites FK references in other tables since 3.26); use new names for new tables instead.
- Treating the generic init() catch as the migration error path (see Pattern 2).
- Dropping any legacy table in 2.1.
- `INSERT..SELECT` with INNER JOIN on parents (silently drops rows whose parent is missing). Always LEFT JOIN and let verification count.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| "Checksum" of migrated data | custom hashing | two-way `EXCEPT` in SQL | exact, zero code |
| Testing sqflite code without a device | mocks of `Database` | sqflite_common_ffi + real SQLite | verified working here |
| Version pruning on the server | JS logic per item | trigger + `entity_prev` PK (table, uuid) — overwrite = exactly 1 previous | one row per entity by construction |
| Atomic batch | manual rollback | `sql.transaction([...])` (already used) + `DEFERRABLE INITIALLY DEFERRED` FKs | order-independent within a batch |
| Deterministic uuids | random + mapping table | uuid v5 (Dart `Uuid().v5(ns, name)`; Node sha1 helper) | both migrations agree without talking |
| Spatial coverage | PostGIS | 4 min/max + center columns + btree index | D-16 |

## Answers to the specific questions

### Q1. SQLite migration technique (HIGH for mechanics, verified in sqflite source)
Procedure (all inside `onUpgrade`'s transaction): create new tables -> populate (LEFT JOIN mapping int FK -> parent uuid) -> local-only tables -> outbox rebuild -> verify (throws) -> rename legacy tables -> `sync_state` cursor reset. sqflite sets `user_version` inside the same transaction, so a rollback also keeps version 6.
- Transaction semantics: `doOpen` wraps onCreate/onUpgrade/onDowngrade + `setVersion` in `transaction(..., exclusive: true)`; `onConfigure` runs outside it. Exception -> rollback -> `openDatabase` throws. SQLite DDL (CREATE/ALTER/RENAME) is transactional, so "no DDL rollback assumptions" is unnecessary here — but the migration test must still prove it (test: force a verification failure and assert the DB is still v6 with all legacy tables and no new tables).
- PRAGMA foreign_keys: no-op inside a transaction; the app has FKs off; leave off. Use `PRAGMA foreign_key_check` for verification.
- WAL/journal: checkpoint + close before copying, copy sidecars too, verify the copy (Pattern 2). Reuses Phase 1's `formatRecoveryTimestamp`.
- Pitfalls: `db.execute` runs ONE statement; big `batch` inside the open transaction is fine (`commit(noResult: true)`); keep the mapping of uuid-less rows explicit (see Q3).

### Q3. Mapping rules and pre-flight (MEDIUM: shapes from code, counts must come from the real copy)
| Legacy | New | Rule |
|--------|-----|------|
| `audio_assets` (77) | `audios` (77) | uuid preserved, `kind='grabacion'`; `local_path`/`remote_url` -> `audio_local`; `artist` text dropped from new model (kept in `legacy_audio_assets`) — see Open Questions |
| `geo_paths` (70) | `paths` (70, `kind='route'`) + `obras` (70) | path uuid preserved; obra uuid = `v5(NS,'obra:'+path_uuid)`, name = path name, `draft`, `updated_at`/version taken from the path (`logical_version=1`) so server + phone generate identical rows; `audio_uuid` from path's audio (JOIN); `saved_offset_ms` -> `path_progress` |
| `geo_triggers` with path | `triggers` | uuid preserved; `path_uuid` from JOIN; `position` by `(offset_ms, id)`; trigger's own `audio_asset_id` and `region_id` are NOT carried (archived in legacy) |
| `geo_triggers` standalone (`geo_path_id` NULL) | `triggers` + portal `paths` + `obras` | trigger uuid preserved; portal path uuid = `v5(NS,'portal:'+trigger_uuid)`, `kind='portal'`, `audio_uuid` = the trigger's audio; obra uuid = `v5(NS,'obra:'+portal_path_uuid)`, named after the trigger, draft. **D-12 does not say portals get their own obra, but a path must belong to an obra (D-02), so 1:1 is implied; flag to the planner.** |
| `regions` (20), `region_id` | legacy tables only | renamed, not dropped |

Behaviour check (verified in `monitor_user_location_usecase.dart` lines ~253-271, 310): when a trigger has `geoPathId` the monitor plays the PATH's audio, ignoring the trigger's own `audioAssetId`; only standalone triggers play their own audio. So dropping trigger audio for path-triggers loses no current behaviour, and portals carry the trigger's audio at path level. "Playback behaves as today" holds. The monitor must be re-pointed: trigger -> `path_uuid` -> path -> `audio_uuid` (for all triggers now).

**Pre-flight report** (`preflight(db)` returns a map; run in the unit test, in the migration (logged/embedded in the exception), and once by hand on the DB copy BEFORE writing any code that assumes cleanliness). Count and list ids for:
1. rows with `uuid IS NULL` per table — very likely for seed rows (`SeedData` inserts WITHOUT uuid; only `onCreate` seeds; `ALTER ... ADD COLUMN uuid` in v4 left old rows NULL; nothing backfills; `saveProgress`/`updateAudio` assign uuids only when they touch a row). Neon's 626 = 77+70+459+20 suggests everything was pushed, which conflicts with NULL uuids existing — verify on the copy. Rule: assign a fresh v4 to NULL-uuid rows inside the migration (they never reached the server, so the phone's full resend delivers them).
2. duplicate uuids (column has no UNIQUE); invalid uuid format (regex) — server casts to `uuid`.
3. NULL `logical_version` / `updated_at` -> `COALESCE(logical_version,1)`, `updated_at` fallback to migration time (server requires `>= 1`).
4. audios referenced by no path and no trigger (orphans: still migrated as `audios`).
5. triggers whose `geo_path_id` points to a missing path (decide: treat as standalone portal only if it has an audio; otherwise migrate with `path_uuid` of an auto-created portal path; NEVER drop — legacy table keeps the row, verification counts "explained" ids in the report); triggers whose `audio_asset_id` is missing; paths whose `audio_asset_id` is missing (-> `audio_uuid NULL`).
6. path triggers whose audio differs from the path's audio (informational; no behaviour change per the check above).
7. `INTEGER PRIMARY KEY` without AUTOINCREMENT: ids can be reused after deleting the highest row (matters for Neon Q5, not the phone).
8. soft-deleted rows (`deleted_at NOT NULL`) — nothing sets it today; migrate as-is.
9. outbox: counts by `table_name`/`op`; rows for `regions`; delete rows with thin payloads.
10. `local_path` values that are asset paths vs files (informational; must be preserved verbatim).

### Q4. Server schema (MEDIUM-HIGH: standard Postgres; Neon-driver facts verified)
```sql
CREATE SEQUENCE IF NOT EXISTS change_seq;                       -- one global sequence = one pull cursor
-- every synced table:
--   uuid uuid PRIMARY KEY, logical_version int NOT NULL CHECK (logical_version >= 1),
--   updated_at timestamptz NOT NULL, deleted_at timestamptz,
--   change_seq bigint NOT NULL DEFAULT nextval('change_seq')      + index on change_seq
audios(kind CHECK, title, description, duration_seconds, storage_key, checksum)
artistas(name, bio, user_id uuid)
obras(name, owner_id uuid, visibility CHECK, share_token unique, cover_lat, cover_lon,
      cover_min_lat, cover_max_lat, cover_min_lon, cover_max_lon)     + index (cover_min_lat, cover_max_lat, cover_min_lon, cover_max_lon)
obra_artistas(obra_uuid REFERENCES obras DEFERRABLE INITIALLY DEFERRED, artista_uuid REFERENCES artistas DEFERRABLE INITIALLY DEFERRED, UNIQUE(obra_uuid, artista_uuid))
paths(obra_uuid -> obras, kind CHECK, name, audio_uuid -> audios (nullable), grabacion_uuid -> audios (nullable), tolerance_meters)
triggers(path_uuid -> paths, position, name, description, latitude, longitude, radius_meters, offset_ms)
entity_prev(table_name text, record_uuid uuid, version int, payload jsonb, updated_at timestamptz, PRIMARY KEY (table_name, record_uuid))
```
- **change_seq:** a BEFORE INSERT OR UPDATE trigger sets `NEW.change_seq := nextval('change_seq')` so ANY writer (push, migration script, future web editor) bumps the cursor. Only rows that pass the `ON CONFLICT ... WHERE current.logical_version < EXCLUDED.logical_version` gate fire the UPDATE trigger, so idempotent re-pushes do not move the cursor. `state.js` returns `MAX(change_seq)` across tables (or `last_value` of the sequence) as `serverCursor` (string). Known limitation (MEDIUM, training knowledge): sequence values can commit out of order under concurrency, so a puller could skip a row; irrelevant with one writer, note for Phase 3.
- **SYNC-06 (recommend):** ONE generic `entity_prev` table + ONE plpgsql trigger function `BEFORE UPDATE ... WHEN (OLD.logical_version < NEW.logical_version)` that upserts `(TG_TABLE_NAME, OLD.uuid, OLD.logical_version, to_jsonb(OLD), OLD.updated_at)`. Because the PK is `(table_name, record_uuid)`, overwrite guarantees exactly one previous version. Attach with a `DO $$ ... FOREACH t IN ARRAY ... EXECUTE format(...)` loop. Rejected: 6 history tables (6x DDL + 6x pruning).
- **Upsert in dependency order:** declare all FKs `DEFERRABLE INITIALLY DEFERRED`; the batch then works in any order and is checked at COMMIT (the neon HTTP `transaction()` is one BEGIN..COMMIT). Client FIFO already sends parents first; the Q7 full resend enqueues in rank order too (audios, artistas, obras, obra_artistas, paths, triggers). An FK failure aborts the whole batch (all-or-nothing, as today); map it to a clear 4xx/5xx with the offending ids in the message. Soft-delete on the server (`deleted_at`) means deletes never break FKs.
- **Spec-driven code:** `backend/api/_lib/spec.js` maps `table -> { columns: {name: type, required}, rank }`. `validateOutboxItem` and the upsert both read it (identifiers come only from this static whitelist, never from input; use `sql.query(text, params)` — objects have `queryData`, transaction-compatible, verified structurally; the integration test proves it end-to-end). Generic statement: `INSERT INTO t (...) VALUES (...) ON CONFLICT (uuid) DO UPDATE SET <all cols> WHERE t.logical_version < EXCLUDED.logical_version`. `op:'delete'` -> `UPDATE t SET deleted_at = now(), logical_version = $v WHERE uuid = $u AND logical_version < $v` (no insert of a thin tombstone; unknown uuid = no-op ack). Convert `updated_at` epoch seconds -> `to_timestamp($n)`.
- **Contract versioning (D-20):** request body `{ schema_version: 2, outbox: [...] }`; server returns `400 {error:'schema_version 2 required'}` otherwise. The old app sends no such field and old table names (`geo_paths`, ...) are also rejected by the new whitelist. One integer, no dual protocol. Response shape (`ackedIds`, `serverCursor`, `receivedAt`) unchanged, but `serverCursor` is now a change_seq string; phone resets `sync_state.server_cursor` at migration.
- `schema.sql` is replaced by the typed schema; the existing `push.test.js` (which loads `schema.sql` and asserts `synced_entities`) must be rewritten. Keep `CREATE ... IF NOT EXISTS` so the file is re-runnable.

### Q5. Neon migration script (MEDIUM)
`backend/scripts/migrate_v2.mjs`, plain Node + `@neondatabase/serverless`, run as `node scripts/migrate_v2.mjs [--apply] [--finalize]`; default = dry-run.
1. Require `DATABASE_URL` from env; print the host and the counts (per table, live vs tombstoned) and require `--apply`. `backend/.env` holds a DATABASE_URL (branch unknown — the script must print which host it hit).
2. Read all `synced_entities` (~626 rows) into memory. Build the map `(table, payload.id) -> record_uuid` from LIVE current payloads first, then from `previous_payload`/tombstones. **Report ambiguities and abort if any FK resolves to more than one uuid:** (a) `INTEGER PRIMARY KEY` ids can be reused after deleting the highest row, so two uuids may share `(table, id)`; (b) thin delete payloads (`{uuid, logical_version, geo_path_id|audio_asset_id|id}`) often lack `id` (trigger deletes have none), so the map is not guaranteed complete from current payloads alone.
3. Tombstoned entities: rebuild the typed row from `previous_payload` (full row) with `deleted_at` set and `logical_version = current_version`; entities whose only server state is a thin delete (no previous) cannot fill NOT NULL columns -> skip and list them in the report (nothing is lost: the phone has physically deleted them).
4. Translate: FK ints -> uuids via the map, `region_id` ignored, standalone triggers -> portal path + obra with the same v5 ids as the phone, coverage computed with the same formula as Dart (see Q8), `updated_at` from payload epoch seconds, `logical_version` preserved (`COALESCE(...,1)` with a warning).
5. Apply in ONE `sql.transaction([...])`: run `schema.sql` (typed DDL + triggers), `INSERT ... ON CONFLICT (uuid) DO UPDATE ... WHERE version <` (idempotent, re-runnable to catch stragglers), then verify inside JS after commit (re-query counts): `audios == audio_assets rows`, `triggers == geo_triggers rows (minus skipped tombstones)`, `paths == geo_paths + standalone`, `obras == paths`. Regions stay only in the blob table.
6. `--finalize` (separate, run only after counts match AND the new backend is deployed and verified): `ALTER TABLE synced_entities RENAME TO synced_entities_legacy`. Never DROP.
7. **Rehearsal:** create a throwaway Neon branch from `main` (copy-on-write, includes data; free tier allows 10 branches), run dry-run + apply + verify there, delete the branch, then run on `main`. Point-in-time restore on main is an extra net (training knowledge, verify retention window in the Neon console; LOW-MEDIUM).
8. Order of operations for the cutover (D-20): rehearse on branch -> quiet the app (don't open it; airplane mode) -> run script on main -> deploy new backend -> `--finalize` -> install new app -> first open migrates + resends. Re-running the idempotent script after the deploy catches pushes that landed in the old blob during the window; the phone's full resend is a second catch.
9. Also export a full `synced_entities` JSON dump to a local (git-ignored) file before `--apply`.
- The v5 helper and namespace live in one place per language with the SAME test vector asserted in `flutter test` and `node --test` (generate the expected value with Python `uuid.uuid5` as a third independent check).

### Q6. uuid v4 vs v7 (HIGH that it doesn't matter)
`uuid` locked at 4.5.2 (4.6.0 latest); `Uuid().v7()` exists since 4.0.0. Recommend **v4** for all new client-generated ids: one generator (`SyncLocalDataSource.newUuid()`), no index-locality benefit at this scale, existing rows are v4 and preserved as-is. Postgres column type `uuid`; PKs are ALWAYS client-supplied — do not rely on `gen_random_uuid()` for synced tables. Deterministic ids for auto-created obra/portals use v5 (`Uuid().v5(namespace, name)`; namespace = a fixed constant defined once, documented). Postgres `uuid` accepts any version.

### Q7. Outbox during migration (recommend: rebuild, do not drain)
Draining against the old server is impossible/undesirable under D-20 (server migrates first; the old endpoint shape is gone). Recommended, inside the migration transaction:
1. Rename `sync_outbox` -> `legacy_sync_outbox` (kept for audit).
2. Create a fresh `sync_outbox` (same shape) and enqueue a **full resend of every synced entity** in rank order: audios, artistas, obras, obra_artistas, paths, triggers (~700 rows, tiny), payload = the new-table row. Idempotent by `uuid + logical_version`: identical version -> no-op on the server; entities edited during the no-sync window have higher versions and are applied.
3. **Pending deletes must be translated, not resent:** a full resend cannot express a tombstone. For each legacy outbox row with `op='delete'` on `audio_assets|geo_paths|geo_triggers`, enqueue `{table: audios|paths|triggers, record_uuid, op:'delete', payload:{uuid, logical_version}}`. Drop legacy `regions` rows. Insert/update rows are subsumed by the resend.
4. `attempt_count`/`next_attempt_at` reset to 0/NULL. This also self-heals any drift from the server migration.

### Q8. Derived coverage (recommend: phone computes, server stores)
Single writer today (the phone), so compute on the phone and sync it as ordinary obra columns; the server does NOT recompute on push (two computations = divergence risk). Implementation: one Dart function `computeCover(List<trigger>) -> {minLat,maxLat,minLon,maxLon,centerLat,centerLon}` (center = arithmetic mean of trigger positions, rounded to 6 decimals; min/max rounded the same) and one helper `refreshObraCover(obraUuid)` called from trigger insert/update/delete and once at the end of recording a path; it updates the obra ONLY IF a value changed (bump `logical_version`, enqueue). The same formula (JS port) is used once in the Neon migration script; tests assert identical output on a shared vector. When a web editor arrives (future) it owns recomputation for its edits. No PostGIS, no server triggers. Empty obra (no triggers) -> coverage columns NULL.

## Common Pitfalls

### Pitfall 1: init() catch renames a healthy DB when the migration fails
**What goes wrong:** rollback throws from `openDatabase`; generic catch renames the v6 file and creates an empty v7 DB (looks like data loss).
**How to avoid:** dedicated `MigrationException`, caught before the corrupt-DB path; blocking error screen; test it.
### Pitfall 2: Independent migrations invent different ids
**What goes wrong:** phone and script each create random obras for the same path -> duplicate obras after first sync.
**How to avoid:** uuid v5 with a shared namespace and a cross-language test vector.
### Pitfall 3: `(table, id)` map assumptions
**What goes wrong:** id reuse (no AUTOINCREMENT) or thin delete payloads give wrong/missing parents.
**How to avoid:** live-first map, previous_payload fallback, abort on ambiguity, dry-run report.
### Pitfall 4: NULL uuid / NULL logical_version rows (seed rows)
**What goes wrong:** `NOT NULL PRIMARY KEY uuid` insert fails, or server rejects `logical_version` null.
**How to avoid:** pre-flight counts, COALESCE + fresh v4; test with synthetic NULL rows.
### Pitfall 5: Stale `server_cursor`
**What goes wrong:** old ISO timestamp cursor is sent to a change_seq-based protocol in Phase 3.
**How to avoid:** reset to NULL at migration.
### Pitfall 6: Pending deletes lost by "full resend"
**How to avoid:** translate legacy delete rows (Q7 step 3).
### Pitfall 7: Old-Android SQLite (3.8-3.22)
**How to avoid:** no window functions/RETURNING/UPSERT/DROP COLUMN; test in ffi with SQLite 3.50 will NOT catch this — add a review checklist item.
### Pitfall 8: Tests open the real DB
**How to avoid:** always copy to temp first; env-var path only; fixture never in git.
### Pitfall 9: Old app hitting the new server
**What goes wrong:** old outbox rows keep failing (400) and accumulate attempts. **How to avoid:** irrelevant once the new app is installed (outbox rebuilt); ensure the app's terminal-error handling does not delete rows on 400 (check `SyncClient` before cutover).
### Pitfall 10: Seed on fresh install
`SeedData` inserts old-format rows (with `region_id`). Rewrite minimally to the new shape (with uuids) or drop the seed; do not leave it.
