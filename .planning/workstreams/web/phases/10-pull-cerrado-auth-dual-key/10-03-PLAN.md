    1. En "ERS · Backend — protocolo de sync" agregar una sección `GET /sync/pull` con este contenido
       (en castellano, sin cambiar los valores):

       - **Ruta:** `GET /sync/pull` (el stub de la app usa `/sync/changes` en
         `lib/core/config/api_config.dart:36`; lo corrige `app` Fase 3).
       - **Auth:** `Authorization: Bearer <key>`. Acepta `SYNC_API_KEY` (celular) y `WEB_API_KEY` (web).
         Sin key válida -> `401 { "error": "invalid or missing API key" }`.
       - **Query params:** `cursor` = string con entero >= 0 (si falta: `0`); `limit` = entero entre 1 y
         1000 (si falta: 500). Inválido o fuera de rango -> `400 { "error": "cursor must be an integer >= 0" }`
         o `400 { "error": "limit must be an integer between 1 and 1000" }`. Método distinto de GET -> 405.
       - **Respuesta 200:** `{ "changes": [{ "table", "change_seq", "payload" }], "nextCursor", "hasMore" }`.
         Lista plana en orden global ascendente de `change_seq` (todas las tablas mezcladas).
         `table` ∈ recorridos, audios, artistas, obras, obra_artistas, paths, triggers.
         `payload` = exactamente las columnas de la tabla que acepta el push (spec.js), con
         `updated_at`/`deleted_at` en epoch segundos (entero) o null. `change_seq` y `nextCursor` son
         strings (bigint). `nextCursor` = `change_seq` de la última fila devuelta; si no hay filas, el
         `cursor` recibido. `hasMore: true` = pedir otra página con `cursor = nextCursor`.
       - **Borradas:** fila completa con `deleted_at` != null; sin tombstone especial. El celular aplica
         borrado lógico; la web las filtra. La versión anterior (`entity_prev`) no se expone.
       - **Orden al aplicar:** la respuesta no agrupa padres antes que hijos; el cliente ordena
         (referencia: recorridos, audios, artistas, obras, obra_artistas, paths, triggers).
       - **Garantía de no-salto:** un pull nunca devuelve un `nextCursor` que pase por encima de un
         cambio que todavía no es visible. Paginar con `nextCursor` hasta `hasMore: false` nunca pierde
         filas, aunque haya pushes concurrentes. (No documentar el mecanismo interno acá: vive en ADR-012.)
       - **Cursor válido:** el ÚNICO cursor válido para pull es `0` o un `nextCursor` devuelto por un
         pull. El `serverCursor` de `/sync/state` y de la respuesta del push es informativo: puede estar
         por delante de un push en vuelo, y usarlo como cursor de pull puede saltear filas.
       - **Alcance de keys:** `WEB_API_KEY` es de solo lectura en este milestone: pull y state sí;
         `POST /sync/push` con `WEB_API_KEY` válida -> `403 { "error": "API key is read-only" }`.
       - **/sync/state:** incluye `recorridos` en `serverCursor` y `lastSyncAt` (fix de esta fase).

    2. ADR-007 (`WEB_API_KEY` separada de `SYNC_API_KEY`): agregar UNA línea en "Consecuencias":
