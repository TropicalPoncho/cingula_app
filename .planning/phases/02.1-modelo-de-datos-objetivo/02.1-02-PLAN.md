Índices: `change_seq` en cada una de las 6 tablas sincronizables, `paths(obra_uuid)`, `triggers(path_uuid)`, y `obras(cover_min_lat, cover_max_lat, cover_min_lon, cover_max_lon)` (recomendación de obras cercanas sin PostGIS, D-16).

Dos funciones plpgsql + sus triggers, aplicadas a las 6 tablas con un bloque `DO $$ ... FOREACH t IN ARRAY ARRAY['audios','artistas','obras','obra_artistas','paths','triggers'] LOOP EXECUTE format(...) END LOOP; $$;`:
- `bump_change_seq()` → `BEFORE INSERT OR UPDATE`: `NEW.change_seq := nextval('change_seq'); RETURN NEW;`
- `save_prev_version()` → `BEFORE UPDATE ... FOR EACH ROW WHEN (OLD.logical_version < NEW.logical_version)`: hace `INSERT INTO entity_prev (table_name, record_uuid, version, payload, updated_at) VALUES (TG_TABLE_NAME, OLD.uuid, OLD.logical_version, to_jsonb(OLD), OLD.updated_at) ON CONFLICT (table_name, record_uuid) DO UPDATE SET version = EXCLUDED.version, payload = EXCLUDED.payload, updated_at = EXCLUDED.updated_at; RETURN NEW;`

La PK `(table_name, record_uuid)` de `entity_prev` es lo que hace cumplir SYNC-06 por construcción: sobrescribir = exactamente una versión anterior, sin código de poda. El `WHEN (OLD.logical_version < NEW.logical_version)` es lo que hace que un re-push idéntico (que no actualiza nada por el `WHERE` del upsert) no mueva ni el cursor ni la versión anterior.

**Cargador de statements (`backend/api/_lib/schema_loader.js`).** El `schema.sql` de la Fase 2 era UN solo `CREATE TABLE` y los tests lo cargaban con un único `sql.query(texto)`. Este archivo pasa a ~25 statements e incluye funciones plpgsql con cuerpo `$$ ... $$` y un bloque `DO $$ ... $$`; el driver HTTP de `@neondatabase/serverless` no garantiza multi-statement en una sola llamada (y un split ingenuo por `;` parte los cuerpos `$$` al medio). Por eso el cargador es código, no un detalle del test:

```js
/// Parte el texto en statements de nivel superior. Respeta el dollar-quoting de
/// Postgres ($$ ... $$ y $tag$ ... $tag$), que es lo único que puede contener ';'
/// dentro de este archivo. No pretende ser un parser de SQL: es exactamente lo
/// que hace falta para schema.sql y nada más.
export function splitStatements(sqlText);
export async function applySchema(sql, sqlText = readFileSync(<schema.sql>, 'utf8'));
```
`splitStatements` recorre el texto carácter a carácter con un solo estado (`dentro de $tag$` sí/no), ignora líneas de comentario `--`, y corta en cada `;` de nivel superior descartando los fragmentos vacíos. `applySchema` ejecuta los statements EN ORDEN con `await sql.query(stmt)` (no en transacción: el archivo es re-ejecutable por construcción).
