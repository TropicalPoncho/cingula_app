- `--apply` (x2) and post-migration `npm test`: still not run — blocked by the new validation abort, which happens before any write.

Remediation 2 (this update, same `dev-2.1` branch, new session):
- Re-derived the exact 117-row failure set fresh (not reused from the old log) by re-querying `synced_entities` and re-running `translate()`/`validateOutboxItem`, then traced each failing typed row back to its source `(table, id)` — 90 unique source rows (63 `audio_assets`, 27 `geo_paths`).

## Deviations from Plan

**1. [Rule 4 - architectural, resolved by user] Ambiguous (table,id)->uuid map.** The user inspected the read-only phone DB copy and identified the live uuid for each of the 4 ambiguous keys. Implemented as an explicit override map (`backend/scripts/id_overrides.json`) consumed by `buildIdMap`/`translate`; keys without an override still abort. Files: `backend/scripts/translate.js`, `backend/scripts/translate.test.js`, `backend/scripts/migrate_v2.mjs`, `backend/scripts/id_overrides.json`.

**2. [Rule 4 - architectural, resolved by user] Missing title/name on ~117 rows.** Discovered during the first remediation's re-run, one abort layer past the id-ambiguity fix. Not a bug introduced by this remediation — a pre-existing gap in what's stored in `synced_entities` (old v6 client apparently pushed partial, not full-row, payloads for updates; the base fields fell out of history beyond the server's current+1-previous retention). Resolved in remediation 2: read the real values from the read-only phone DB copy (same source and method the 4 id overrides used) and applied them via a new, separate, uuid-keyed override map (`backend/scripts/content_overrides.json`) — kept separate from `id_overrides.json` because two of the affected `geo_paths` ids (`11`, `12`) overlap with the id-ambiguity set, and a `table:id`-keyed override would have applied to the wrong (discarded) uuid there. Never overwrites a real value (fail-safe: warns and skips instead). Files: `backend/scripts/translate.js`, `backend/scripts/translate.test.js`, `backend/scripts/migrate_v2.mjs`, `backend/scripts/content_overrides.json`.

**3. [Rule 1 - bug, auto-fixed] `pick()` sent explicit `null` for `NOT NULL DEFAULT` schema columns.** Found while completing remediation 2's `--apply` step (Scope: directly blocked finishing the assigned task). `schema.sql` declares `audios.description`/`duration_seconds`, `paths.tolerance_meters`, and `triggers.description`/`offset_ms` as `NOT NULL DEFAULT <value>`; `spec.js`'s `REQUIRED` intentionally doesn't require them (not critical like title/name), so a missing value passed validation as `null` and `pick()` wrote that `null` explicitly, bypassing Postgres's own default and violating the constraint. Root-cause fixed once at `pick()` (the single shared point all six typed tables' rows pass through), not per-caller, with a `COLUMN_DEFAULTS` map mirroring `schema.sql`. Covered by a new test. Files: `backend/scripts/translate.js`, `backend/scripts/translate.test.js`.
