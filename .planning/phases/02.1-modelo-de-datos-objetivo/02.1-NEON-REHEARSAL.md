### Root cause (confirmed by direct query on the same branch, not guessed)

Both `current_payload` AND `previous_payload` for these rows lack `title`/`name` entirely (not null-valued, absent). Example (`audio_assets` uuid `eb3bfeb5-...`, `logical_version` 2):

```
current_payload:  { id, uuid, updated_at, logical_version, duration_seconds }
previous_payload: { id, uuid, title: "quinto escalera", artist, ..., logical_version: 1, duration_seconds: 0 }
```

Direct count: only **5 of 68** `audio_assets` rows in `synced_entities` carry a `title` in `current_payload` at all. For rows edited many times (e.g. `saved_offset_ms`/`duration_seconds`-only pushes from the old v6 client, which apparently sent partial rather than full-row payloads for updates), the base fields (`title`, `name`) fell out of `current_payload` generations ago, and the server's "current + 1 previous version" retention (SYNC-06/MODEL-03) already pruned any version that still had them. The name/title is **not recoverable from `synced_entities`** — only from the phone's local DB, which still holds the full, correct row.

This matters for the cutover design in 02.1-RESEARCH.md (line ~287): the planned full resend after migration is a **same-version no-op** for entities untouched during the no-sync window (`upsertStatement`'s guard is strict `<`, not `<=`). So if this script wrote null/placeholder names now, the phone's future full resend would **not** self-heal them — they'd stay broken permanently unless the resend bumps versions or the migration script is told the real values first.

**Not fixed here** — this needs a decision from the data owner (options include: read the true values from the phone DB copy the same way the 4 id overrides were resolved, and add them as content overrides; or skip these ~117 entities from the typed-table migration and bump their version during the 02.1-12 full resend so the phone's real values do land; or something else). Flagging for 02.1-12 planning, same as the ambiguous-id issue was flagged after Task 3's first rehearsal.

## Content-overrides remediation — 2026-09-22 (same `dev-2.1` branch, new session)

**Goal:** resolve the ~117-row title/name gap above so the full rehearsal (steps a-e) can run cleanly, closing MODEL-06.

### Re-deriving the affected set (fresh query, not reused from the old log)

Re-queried `synced_entities` on `dev-2.1` directly (read-only) and re-ran `translate()` + `validateOutboxItem` to get the exact current list of failing typed rows, then traced each back to its source `(table, id)` via the same reconstruction `translate.js` uses internally (including tombstone-reconstructed rows via `previous_payload`, which the first trace attempt missed for 1 of 117 rows). Result, confirmed fresh:

- **117 typed rows fail** (63 `audios.title`, 27 `obras.name`, 27 `paths.name`) — same total as the original rehearsal.
- These trace back to **90 unique source rows**: 63 `audio_assets` (their own `title`) and 27 `geo_paths` (their own `name`, which feeds both the `obras` row and the `paths` row derived from the same geo_path — that's why obras/paths counts match 1:1 but audios don't overlap with them).
- Two of the 27 `geo_paths` ids (`11`, `12`) are also members of the pre-existing id-ambiguity set (`id_overrides.json`) — confirmed these are a **separate, orthogonal** concern: the *live* uuid chosen by the id override for each is exactly the uuid missing its `name`, so both mechanisms apply to the same row without conflicting (id override picks which uuid is real; content override fills its missing `name`).

### Reading the real values (phone DB copy, read-only)

Copied `C:\Users\ramac\cingula-db-copia\cingula.db` to a session-scoped temp path (never opened the original — sidecar `-wal`/`-shm` files, if any, only ever touched the temp copy) and read it with Node's built-in `node:sqlite` (`DatabaseSync`, `readOnly: true`) — no new dependency, matches the "stdlib first" rule and the project's read-only-copy convention (same spirit as `sqflite_common_ffi` in the Flutter tests, `node:sqlite` is the Node-side equivalent, already ships with Node ≥22 which `backend/package.json` already requires).

Looked up all 63 `audio_assets.title` and all 27 `geo_paths.name` values by primary key `id`. **All 90 found, none null/empty.** No fabricated values — every entry in `content_overrides.json` is a real value read from the phone DB copy.

### Mechanism (`backend/scripts/content_overrides.json`)

`{ uuid: "real title/name" }`, applied by a new `applyContentOverride()` in `translate.js`, called once per entity inside the same loop that already builds `ents.audio_assets`/`ents.geo_paths` (reused the existing loop rather than adding a parallel pass — smaller diff). Rules, covered by new tests in `translate.test.js`:

- Fills `title` (`audio_assets`) or `name` (`geo_paths`) **only when the field is missing** (`undefined`/`null`).
- **Never overwrites** a value that's already present — if an override exists for a uuid that already has a real value, the override is ignored and a warning is logged (`content override para <field> ignorado, ya tiene valor`), never silently dropped and never fail-loud (a stale override shouldn't abort a migration).
- A row missing `title`/`name` **without** a matching override still fails `validateOutboxItem` exactly as before — fail-safe unchanged.

Keyed by `uuid` (not `table:id` like `id_overrides.json`): the id-ambiguity overlap above (`geo_paths:11`/`:12`) means `table:id` would apply the same content override to multiple different uuids sharing that id, including the *discarded* duplicates from the id-override mechanism — wrong. Keying by `uuid` is unambiguous per-entity and keeps the two mechanisms cleanly separate, per the plan's explicit instruction not to conflate them.

### Second, unrelated bug found and fixed while unblocking this: `pick()` sent explicit `null` for `NOT NULL DEFAULT` columns

Once `title`/`name` stopped aborting the *validation* step, the first real `--apply` attempt hit a **new** failure one layer further in — a Postgres `NOT NULL` constraint violation on `audios.description`, then (after fixing that) on `paths.tolerance_meters`. Root cause: `schema.sql` declares `description` (`audios`, `triggers`), `duration_seconds` (`audios`), `tolerance_meters` (`paths`), and `offset_ms` (`triggers`) as `NOT NULL DEFAULT <value>` — but `spec.js`'s `REQUIRED` list intentionally does **not** require them (they're not critical like `title`/`name`), so `validateOutboxItem` let a missing value through as `null`, and `translate.js`'s `pick()` then wrote that `null` explicitly into the `INSERT`, bypassing Postgres's own column default entirely. This was **never reached before** because the `title`/`name` abort always happened first for the same rows (all 63 affected `audio_assets` rows were also missing `description`).

Fixed at the single shared point (`pick()`, root-cause fix, not per-caller): a small `COLUMN_DEFAULTS` map mirrors `schema.sql`'s own `DEFAULT` values, and `pick()` falls back to it before falling back to `null`. Covered by a new test asserting both the audios case (`description`/`duration_seconds`) and the paths case (`tolerance_meters`). Not a content-override concern, but a blocking bug hit while completing this remediation — fixed per Rule 1/3 (root-cause bug fix at the shared code path, in scope because it directly blocked finishing this task's `--apply` step).
